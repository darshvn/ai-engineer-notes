01

Writing a file, then reading it back

Reading/writing text files
Where we areEverything so far lived in variables, and variables vanish when the program stops.
What we haveA few strings.
What we wantThe strings in a file, and back in the program next time.
How1 · Open→2 · Write or read→3 · Close
See it

Write two lines, add a third, read everything back:

with open("notes.txt", "w", encoding="utf-8") as f:
    f.write("tokens\n")
    f.write("embeddings\n")

with open("notes.txt", "a", encoding="utf-8") as f:
    f.write("attention\n")

with open("notes.txt", encoding="utf-8") as f:
    for n, line in enumerate(f, start=1):
        print(n, repr(line))
    print(repr(f.read()))
1 'tokens\n'
2 'embeddings\n'
3 'attention\n'
''
Words
file object
What open() hands back. It holds a position in the file (CampusX calls it the buffer, or the cursor) that moves as you read or write.
mode
The second argument. "r" read (the default), "w" write, "a" append, "x" create only if new. Add "b" for bytes instead of text.
encoding
The rule for turning characters into bytes on disk. "utf-8" handles every language.
context manager
The with block. It closes the file when the block ends, even if an error happens inside it.
Walk it

"w" empties the file the moment it opens, before a single write. That's why the first block starts clean every run. "a" opens with the position at the end, so the third line lands after the first two.

write() writes exactly what you give it. Unlike print(), it adds no newline, so every \n above is there on purpose.

Reading comes in three sizes. read() returns the whole file as one string, readline() one line, and for line in f one line per loop. On a 50 MB file of 100-character lines, read() held all 50,000,000 characters in memory at once; the loop held 100.

Once the position reaches the end, read() returns an empty string, not an error. That empty string is how a loop knows the file is finished.

Opening a file doesn't load it. Writes collect in a small buffer (8,192 bytes) and reach the disk when it fills or when the file closes. After write("Hello world") returned 11, the file on disk was still 0 bytes; it became 11 at close(). That's the real reason to close, and why with matters: a file left open can lose its last writes.

"w" deletes first, asks never

Open last month's report with "w" by mistake and it's empty before your first write. Use "a" to add, or "x" to refuse if the file already exists.

Always say the encoding

Without encoding=, Python uses the machine's default. It's UTF-8 on this Mac, but often cp1252 on Windows, where a file with "₹" or Hindi text written on one machine can fail to read on the other.

The rule

Open inside a with block, with the mode you mean and encoding="utf-8". Write the newlines yourself. Read line by line when the file could be big.

You open an existing report.txt with "w", then the program crashes before its first write(). What's in the file now?

Show answer
Nothing. "w" truncated it at open(), before any write ran. The crash didn't cause the loss; the mode did.

02

Tables and nested data: CSV and JSON

CSV, JSON handling
Where we areSection 01 saved plain text.
What we haveA list of records, each a dict with a number and a tuple inside.
What we wantSave them so Excel, pandas or another program can read them, and get the same values back.
How1 · Serialise→2 · Write→3 · Read→4 · Check the types
See it

The same two records, saved once as CSV and once as JSON, then read back. Asha's record went in as {"name": "Asha", "score": 92, "tags": ("python", "sql")}:

CSV : '92' "('python', 'sql')"
JSON: 92 ['python', 'sql']
Words
serialisation
Turning a Python object into text or bytes that can be stored or sent. Deserialisation is the way back.
CSV
Comma-separated values: a table, one row per line, every cell plain text.
JSON
JavaScript Object Notation: nested objects and lists, the format of almost every web API.
Walk it

CSV only knows text. The score came back as the string '92', and the tuple was written as its printed form, "('python', 'sql')". Types are your job on the way back: int(row["score"]). Pandas' read_csv guesses them for you, which is why it feels different.

Open CSV files with newline="". The csv module writes its own line endings, and without this Windows gets a blank line between every row.

JSON keeps structure, not every type. The number came back a number, but the tuple came back a list, because JSON has one kind of list and both are written as it. JSON stores only strings, numbers, true/false, null, lists and dicts. Anything else changes or fails: dict keys become strings ({1: "a"} loads as {'1': 'a'}), and a set or a date raises TypeError. Passing default=str turns a date into "2026-09-21"; for your own classes, default= takes a function that returns a dict.

dump/load work on files, dumps/loads on strings. The s stands for string.

JSON keys are always strings

Save {2024: "joined"} and load it, and data[2024] is now a KeyError; the key is "2024". It fails far from where the file was written, which makes it slow to find.

The rule

CSV for flat tables that anything can open, knowing every value comes back as text. JSON for nested data passed between programs, knowing only basic types survive. Check the types after every round trip.

A CSV row reads back as {"score": "92"}. You compute row["score"] * 2. What do you get?

Show answer
"9292", not 184. Multiplying a string repeats it. Convert first: int(row["score"]) * 2.

03

Pickle: exact copies, with a catch

Pickle (pros & cons)
Where we areSection 02: JSON refused the set, and it would refuse a class instance too.
What we havePython objects of any kind: a custom class, a set, a tuple.
What we wantSave them and get back exactly the same objects.
How1 · pickle.dumps→2 · Write bytes→3 · pickle.loads
See it

A dict holding a Student object, with a set of skills inside it, and a tuple of scores. Pickled, saved, loaded:

Student ['python', 'sql'] (92, 78)
first bytes: b'\x80\x04\x95g\x00\x00\x00\x00\x00\x00\x00}'

A real Student came back, the set is still a set, and the tuple is still a tuple. The file itself is bytes, not text.

Words
pickling
Python's own serialisation. Unpickling rebuilds the objects from the bytes.
binary mode
"wb" and "rb". Pickles are bytes; dump one into a "w" file and you get TypeError: write() argument must be str, not bytes.
Walk it

The pro: almost any Python object round-trips exactly, with no conversion code. That's why it's common for caching intermediate results and for saving scikit-learn models.

The cons: other languages can't read it, and you can't read it either. A pickle stores the object's data and the name of its class, not the class's code. Load it where Student isn't defined and you get AttributeError: Can't get attribute 'Student' on <module '__main__'>. Renaming the class breaks every old file the same way.

The serious con: unpickling can run code. The exercise makes a class whose pickle tells loads() to call print, and the line prints during loading. A malicious file would name something worse than print. It's why Hugging Face created the safetensors format for model weights.

"It's just data" is wrong

A pickle is closer to a small program than to a data file. Never load one that came from someone else: a download, an upload, an email attachment.

The rule

Pickle for your own short-lived, Python-only caches. JSON for anything shared, kept long, or read by other tools. Never unpickle data you didn't create.

A teammate emails you model.pkl. Is loading it with pickle.load safe if you trust the teammate?

Show answer
Only as safe as every machine and inbox it passed through. Loading runs whatever the file says. Ask for a format that can't run code, such as JSON for settings or safetensors for weights, or load it in a throwaway environment.

Folders, paths and where Python is standing

Working with directories (os, pathlib)
Where we areEvery file so far sat in one folder.
What we haveA project with nested folders and a mix of files.
What we wantCreate folders, find files, rename them, and have it work on any machine.
How1 · Build a path→2 · Create or list→3 · Change
See it

The exercise builds project/data/ with b.csv, a.csv, notes.txt and raw/c.csv, then looks around:

glob     : ['a.csv', 'b.csv']
sorted   : ['a.csv', 'b.csv']
parts    : a .csv data
after    : ['a.csv', 'b.csv', 'notes.md', 'raw']
relative : False
Words
path
A file's address. Absolute paths start at the top of the disk; relative paths start from the current working directory.
current working directory
The folder you ran Python from. Not the folder the script lives in.
glob
A filename pattern: *.csv matches CSVs in one folder, **/*.csv in every folder below it.
Walk it

pathlib.Path treats a path as an object. / joins parts correctly on every OS, and .stem, .suffix and .parent pull it apart: a, .csv, data. mkdir(parents=True) created data and raw in one call. open() won't do that for you: writing to no_such_folder/x.txt raises FileNotFoundError until the folder exists.

The older os module does the same jobs with plain strings, and you'll see both in other people's code:

Jobpathlibos
joinPath("data") / "a.csv"os.path.join("data", "a.csv")
make foldersp.mkdir(parents=True, exist_ok=True)os.makedirs(p, exist_ok=True)
listp.iterdir(), p.glob("*.csv")os.listdir(p)
existsp.exists()os.path.exists(p)
renamep.rename(new)os.rename(p, new)

Now the False. The script ran from exercises/, so Path("data") meant exercises/data, not the folder the script built. Relative paths follow where you're standing. Every exercise anchors on Path(__file__).parent, the script's own folder, for exactly this reason.

glob came back alphabetical five runs out of five on this Mac, but Python makes no promise about order; it's whatever the operating system hands back. Wrap it in sorted() when order matters.

Works from one folder, breaks from another

open("data/scores.csv") runs fine from the project folder and raises FileNotFoundError from anywhere else. Build the path from Path(__file__).parent and it works wherever you start.

The rule

Build paths with pathlib from an anchor you control, usually Path(__file__).parent, never from wherever Python happened to be started. Sort anything whose order you rely on.

Logs that outlive the terminal

Logging to files
Where we areScripts report what they did with print(), and it disappears with the terminal.
What we haveA job that runs while you're not watching.
What we wantA file that records what happened, how serious each event was, and the full error when something broke.
How1 · Configure once→2 · Log at a level→3 · Read the file
See it

Four messages at four levels, with logging pointed at app.log. This is the file afterwards:

INFO     etl: loaded 250 rows
WARNING  etl: 3 rows had no score
ERROR    etl: average failed
Traceback (most recent call last):
  File "…/exercises/python/07/05_logging.py", line 18, in <module>
    1 / 0
    ~~^~~
ZeroDivisionError: division by zero

The debug message is missing, and the error came with its full traceback.

Words
logger
A named source of messages: logging.getLogger("etl"). In a module, use __name__ so each line says which file spoke.
level
How serious a message is: DEBUG < INFO < WARNING < ERROR < CRITICAL.
handler
Where messages go: a file, the screen, or both. basicConfig(filename=…) sets up a file handler for you.
Walk it

The level is a threshold. Set to INFO, it lets INFO and everything above through, so the debug line was dropped. With no configuration at all the threshold is WARNING, which is why log.info() on its own seems to print nothing.

log.exception() inside an except block logs at ERROR and appends the traceback. In a real incident that's usually the line that tells you what went wrong.

Pass values as arguments, log.info("loaded %d rows", 250), not as an f-string. The text is only built if the line actually gets written.

A log file opens in append mode, so it grows across runs. The exercise deletes it first so the output stays the same each time.

basicConfig only works once

The first call wins; a second is silently ignored. In a test, the second configuration received nothing at all. If an imported library configured logging first, yours does nothing. Pass force=True to replace it.

Logs get shared

Log files end up in bug reports and chat threads. Never log API keys, passwords or personal data.

The rule

Configure logging once, at the start, with a file and a level. Log through a named logger at the level each event deserves, and use log.exception inside except so errors arrive with their traceback.

Your log.info(...) lines appear nowhere, not on screen and not in the file. Name two likely causes.

Show answer
The level: nothing configured, so the threshold is WARNING and INFO is dropped. Or configuration already happened: something called basicConfig first, so yours was ignored. force=True fixes the second.
