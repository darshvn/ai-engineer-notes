Names, Not Variables

Python core fundamentals, each starting from code you can run and its real output — then the rule that output demonstrates.

How to read this

Every section runs the same four steps: see real code and its real output, get the words, walk through what happened, then state the rule.

Every output on this page was produced by actually running the code, not written from memory. Run them yourself — they're all short enough to paste into a terminal, and predicting the output before you press enter is the whole point.

01

Indentation is grammar, not style

See it

These two programs differ by four spaces. They do completely different things:

for i in [1, 2, 3]:
    total = total + i
print(total)          # runs once, after the loop

for i in [1, 2, 3]:
    total = total + i
    print(total)      # runs three times, inside the loop
Words
block
A group of lines that belong together — the body of a loop, a function, an if. Most languages mark these with { }. Python marks them with indentation alone.
PEP 8
Python's official style guide. Four spaces per level.
Walk it

In most languages, indenting is a favour to the reader — the braces decide what's in the loop. In Python there are no braces, so the indentation is what the parser reads. Your whitespace is part of the program.

Two consequences follow immediately:

  • Never mix tabs and spaces. Python 3 refuses to guess and raises TabError. Set your editor to four spaces and forget about it.
  • Naming conventions carry meaning, so those are the part of PEP 8 worth memorising. The rest a formatter will handle.
FormUsed forExample
snake_casefunctions, variablesparse_config
PascalCaseclassesHttpClient
UPPER_SNAKEconstantsMAX_RETRIES
_leading“internal, don't touch”_cache
The underscore makes nothing private

_cache is a note to humans. Python will happily let anyone read and change it. The only mechanical effect is that from module import * skips it.

The rule

Indentation is how Python decides what's inside what. It is parsed, not decorative — which is why style matters more here than in brace languages.

Why can't Python have the “dangling else” ambiguity that C and Java have?

Show answer
Because indentation makes nesting unambiguous by construction. In C, an else without braces could belong to either of two nested ifs; in Python, its indentation already says which one. A real design win, not just a style preference.
02

Names, not variables

See it

Run this. The output surprises almost everyone the first time:

a = [1, 2]
b = a
b.append(3)
print(a)

[1, 2, 3]      # ← we never touched a
Words
object
The actual thing that exists in memory — the list [1, 2] itself.
name
A label stuck onto an object. a is a name, not a box holding a value.
binding
Attaching a name to an object. That's all = does.
mutate
Change an object itself, in place. .append() mutates.
rebind
Move a name to a different object. = rebinds.
Walk it

b = a copied nothing. It stuck a second label on the same list. So b.append(3) changed the one list that both names point at — and reading a afterwards shows the change.

Now the crucial contrast. Same start, one character different, opposite result:

a = [1, 2]        │   a = [1, 2]
b = a             │   b = a
b.append(3)       │   b = b + [3]
                  │
a → [1, 2, 3]     │   a → [1, 2]
b → [1, 2, 3]     │   b → [1, 2, 3]
                  │
mutated the object│   built a new one,
both names see it │   moved only b
One more, because it catches everyone

== asks “same value?”. is asks “same object?”. Watch what happens with two numbers that are obviously equal:

a = 256;  b = int('256')
print(a is b)     → True

x = 257;  y = int('257')
print(x is y)     → False       # same code, different answer
print(x == y)     → True

Real output from CPython. Small integers from −5 to 256 are pre-made and reused; 257 isn't.

The lesson isn't “remember 256.” It's that is on numbers gives unpredictable answers depending on how the value was created. Use is only for None, True and False, which really are one-of-a-kind objects.

The rule

A name is a label on an object, not a box holding a value. = moves a label. Methods like .append() change the object every label points at.

A function does data = data + [1]. Does the caller's list change?

Show answer
No. That builds a new list and points the function's local name at it. The caller's name still labels the original. Had it been data.append(1), the caller would see the change.
03

Types, casting, and reading input

See it

The single most common beginner traceback, and why it happens:

age = input("age: ")     # you type 30
print(age > 18)

TypeError: '>' not supported between
           instances of 'str' and 'int'

# because:
print(age)               → 30        # looks like a number
print(type(age))         → <class 'str'>  # isn't one
Words
dynamically typed
A name has no fixed type. x = 5 then x = "hello" is fine.
strongly typed
Objects do have types, and Python won't quietly mix them. "3" + 4 is an error, not "34" or 7.
casting
Building a new object of another type from an existing one: int("30").
Walk it

input() always returns a string. Always — even when what you typed looks like a number. Python then refuses to compare a string with an integer rather than guessing what you meant. The fix is int(input("age: ")).

That refusal is a feature. JavaScript would have quietly returned something, and you'd find out much later.

Note also that casting constructs, it doesn't reinterpret — which is why int("30.0") fails. The integer parser doesn't accept a decimal point. You need int(float("30.0")).

The rule

Names have no type; objects do, and Python enforces them. input() hands you a string every time.

What does "5" * 3 give — an error, 15, or something else?

Show answer
"555". String times integer is defined as repetition, so it isn't a type error. Strong typing means Python won't guess — not that every mixed operation fails. "5" + 3 does fail, because no meaning is defined for that.
04

Loops and what counts as true

See it

Real output. Two of these surprise people:

bool(0)       → False
bool('')      → False
bool('0')     → True     # a non-empty string
bool(' ')     → True     # a space is a character
bool([])      → False
bool([0])     → True     # a list holding one thing
bool(None)    → False
Words
truthy / falsy
What a non-boolean becomes when used in an if. Empty things are falsy; everything else is truthy.
iterate
Walk through something item by item. Python's for only does this — there is no counting loop.
Walk it

The pattern is simple once you see it: empty is false, non-empty is true. '0' is truthy because it's a string with one character in it — Python isn't looking at what the character means.

Where this bites

if not count: is true when count is 0 and when count is None. Those usually mean very different things — “we counted, there were none” versus “we never counted.”

When the difference matters, write if count is None: and say what you actually mean.

On loops: Python's for is a for-each, not a counter. Writing for i in range(len(xs)) is transliterated C and is where off-by-one bugs live:

for i in range(len(xs)):   print(xs[i])     # C, in Python costume
for x in xs:               print(x)         # Python
for i, x in enumerate(xs): print(i, x)      # when you need the index too
The rule

Empty containers, zero, empty string and None are falsy; everything else is truthy. for walks over items, never over indices.

A user submits a form field containing "0". Does if not field: treat it as empty?

Show answer
No — "0" is a non-empty string, so it's truthy and not field is False. This is the right behaviour and catches people out constantly: the string "0" and the number 0 behave oppositely here.
05

Functions, and the default-argument trap

See it

Real output. This one costs everybody an hour once:

def add(item, bucket=[]):
    bucket.append(item)
    return bucket

add(1)    → [1]
add(2)    → [1, 2]       # ← expected [2]
add(3)    → [1, 2, 3]    # ← expected [3]

And here is the proof of what's happening — you can look directly at the stored default:

add.__defaults__   → ([1, 2, 3],)

# the "empty" list is an object living on the function,
# and it has been filling up the whole time
Words
default argument
A value used when the caller doesn't supply one.
def-time vs call-time
The def line is itself a statement that runs, once, when Python first reads it. The body runs later, on every call. Defaults are built at def-time.
Walk it

The [] is evaluated once, when the def statement executes, and the resulting list is stored on the function object. Every later call that doesn't pass a bucket reuses that same list. It isn't recreated, because nothing re-runs the def line.

With an immutable default like 0 or "x" this is invisible — you can't change them, so sharing doesn't matter. With a list or dict, it's a shared bucket that fills up.

# the fix — None is immutable, so it can't accumulate
def add(item, bucket=None):
    if bucket is None:
        bucket = []          # a fresh list, per call
    bucket.append(item)
    return bucket

add(1)    → [1]
add(2)    → [2]          # fixed
A second trap from the same fact

xs = xs.sort() leaves xs as None. Real output: [3,1,2].sort() returns None and sorts the list in place.

Python's in-place methods return None deliberately, so that this mistake fails loudly instead of silently. Use sorted(xs) when you want a new list back.

The rule

Default arguments are created once, when def runs — not on each call. Never use a mutable object as a default; use None and build the real value inside the body.

Is def f(x, n=0) affected by this trap?

Show answer
No. The single shared 0 is still shared, but integers are immutable — nothing can modify it, so no state accumulates. The trap needs a mutable default: a list, dict or set.
06

Lambdas

See it

A lambda is a function written inline, where a full def won't fit:

sorted(rows, key=lambda r: r.score)            # sort by score
sorted(rows, key=lambda r: (-r.score, r.name))  # score desc, then name
Words
expression
Something with a value: 2 + 2, r.score. Can be passed as an argument.
statement
Something that does a thing: if, for, def. Has no value, can't be passed.
Walk it

def is a statement, so it can't go inside a function call. lambda is an expression, so it can. That's the entire reason lambda exists.

It's also the entire limit: its body must be a single expression. No if blocks, no loops, no assignment. Not a lesser def — a different grammatical category.

Don't name one. f = lambda x: x * 2 works, but a def carries its name into error messages while a lambda shows up as <lambda> — losing exactly the information you wanted when something breaks.

Late binding — real output 
fs = [lambda: i for i in range(3)]
[f() for f in fs]          → [2, 2, 2]   # not [0, 1, 2]

fs = [lambda i=i: i for i in range(3)]
[f() for f in fs]          → [0, 1, 2]   # fixed

The lambda captured the name i, not its value. By the time you call them the loop has ended with i at 2, so all three report 2. Making i a default freezes the value — because, from §5, defaults are evaluated at def-time.

The rule

lambda is a function you can write in the middle of an expression. One expression only, and don't give it a name — if it needs a name, it needs a def.

Why does the i=i trick fix late binding?

Show answer
Because defaults are evaluated when the lambda is created, not when it's called — so each lambda stores its own copy of i at that moment. The same def-time behaviour that causes the bug in §5 fixes the one here.
07

Comprehensions

See it

The same operation written both ways:

# the loop
out = []
for x in xs:
    if x > 0:
        out.append(x * 2)

# the comprehension — same result, one line
out = [x * 2 for x in xs if x > 0]
       └ output  └ iterate   └ filter
Words
comprehension
A one-line way to build a list, dict or set from something you can iterate over.
generator
Produces items one at a time, on demand, instead of building the whole collection at once.
Walk it

Written left to right the parts read output → iterate → filter. Executed, they run in the opposite order: iterate, then filter, then build the output. Mentally unrolling it into the loop above is the reliable way to read a dense one — and when that unrolling takes real effort, write the loop instead.

The brackets pick what you get back:

[x * 2 for x in xs]       # list
{x: x * 2 for x in xs}    # dict — note the colon
{x * 2 for x in xs}       # set — removes duplicates
(x * 2 for x in xs)       # generator — NOT a tuple

That last one catches people. Parentheses don't give a tuple — there is no tuple comprehension. They give a generator, which computes items only as you ask for them. That's a real difference, not a technicality: sum(x*x for x in big) never builds a list at all, so it uses the same tiny amount of memory whether big has ten items or ten million.

The rule

A comprehension states what the collection is. Use it when it fits on one line. When you need to explain how it's built, the loop is clearer.

You need the sum of squares of 10 million numbers. Square brackets or round?

Show answer
Round. sum(x*x for x in nums) is a generator — it produces one value at a time and never holds all 10 million in memory. Square brackets would build the entire list first, purely to add it up and throw it away.
