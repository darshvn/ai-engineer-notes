Names, Not Variables

Python core fundamentals, revisited from the far side — not how the syntax works, but which parts of it will quietly cost you an afternoon two months from now.

How to use these notes

You've already worked through this section, so this isn't a tutorial — it's consolidation. It skips what you can look up and concentrates on the handful of mechanisms that generate most real Python bugs, plus the reasons behind conventions that otherwise look arbitrary.

Same format as the rest of the set: every idea in prose and as a diagram, and a retrieval bank at the end instead of a summary. Answer those from memory before you re-read anything — recognising a concept and being able to produce it are different skills, and only the second one survives contact with a bug.

01

Syntax, indentation and PEP 8

In C, Java or JavaScript, braces define blocks and indentation is a courtesy to the reader. In Python indentation is the block delimiter. Your whitespace is parsed.

This is why style matters more here than in most languages: formatting is load-bearing. The tokenizer emits INDENT and DEDENT tokens the same way another language's lexer emits { and }. A misplaced space isn't untidy, it's a different program — or a SyntaxError.

Two consequences worth internalising:

  • Never mix tabs and spaces. Python 3 refuses to guess and raises TabError. Four spaces, always — that's PEP 8, and every formatter assumes it.
  • The dangling-else bug can't exist in Python. Indentation makes nesting unambiguous, which is a genuine design win, not just a stylistic preference.

PEP 8 is a negotiation you should stop having. Its real value isn't that its choices are optimal — it's that they're settled, so nobody spends review time on them. Run black or ruff format and stop thinking about it. The parts worth actually remembering are the naming conventions, because those carry meaning rather than aesthetics:

Misconception

“A single leading underscore makes something private.” It makes nothing private. It's a message to humans, and the only thing it changes mechanically is that from module import * skips it. Python has no access control — it has conventions and the expectation that you're an adult about them.

02

Variables, data types and casting

Python has no variables in the C sense. It has names bound to objects. Almost every confusing Python bug you will hit this year is this one fact wearing a different hat.

A C variable is a labelled box holding a value; assignment copies bytes into the box. A Python name is a label attached to an object that lives elsewhere; assignment moves the label. Nothing is copied, ever, unless you ask.

a = [1, 2] b = a # not a copy — a second label on the same list b.append(3) print(a) # [1, 2, 3]

The distinction that follows is the one to burn in: rebinding a name is not the same as mutating an object.

Python is dynamically but strongly typed. Those are different axes and conflating them causes confusion. Dynamic means a name has no declared type and can be rebound to anything. Strong means the object's type is enforced — "3" + 4 raises TypeError rather than silently producing "34" or 7 the way JavaScript or PHP would.

Casting is construction, not reinterpretation. int("42") doesn't relabel bytes; it parses a string and builds a new int object. Which is why int("42.0") raises ValueError — the int parser doesn't accept a decimal point. You want int(float("42.0")).

Misconception

“is and == are interchangeable, I tested it.”

== asks “equal value?”; is asks “the same object?”. Your test worked because CPython caches small integers (−5 to 256) and interns short strings, so 256 is 256 is True and 257 is 257 may not be. That is an implementation detail, not a language guarantee. Use is for None, True and False only — those are genuine singletons.

03

Input, output, comments and docstrings

A comment is discarded by the compiler. A docstring is an object attached to the function at runtime. That difference is why one of them is worth writing carefully.

A string literal in the first statement position of a module, class or function is bound to __doc__ and survives into the running program. It's what help() prints, what your IDE shows on hover, what pydoc and Sphinx extract, and what a doctest runner executes. A # comment is gone before the bytecode exists.

def retry(fn, attempts=3): """Call fn until it returns without raising. Raises the final exception if every attempt fails. """ # ← reachable as retry.__doc__ # a note to the next reader — gone at compile time ...

The rule of thumb worth keeping: comments explain why, code explains what. A comment restating the code is worse than none, because it's a second thing that can drift out of date — and the compiler will never tell you it has.

On print and f-strings. f-strings (3.6+) aren't only terser, they're faster — formatting is compiled into the bytecode rather than dispatched at runtime through str.format. Two features worth knowing because they save real debugging time:

value = 42 print(f"{value=}") # value=42 — self-labelling, 3.8+ print(f"{value:>8,.2f}") # 42.00 — align, thousands, precision print(f"{obj!r}") # uses repr(), not str() — shows quotes and type
Worth knowing early

input() always returns a string. Always. input("age: ") giving "30" and then age > 18 raising TypeError is the single most common beginner traceback, and it's the strong-typing rule from §2 doing exactly what it should.

04

Control flow

Python's for is not a counting loop wearing different syntax. It is a for-each over anything that can produce an iterator — which is why range(10**9) costs no memory.

There is no three-clause for (i=0; i<n; i++). for x in thing: calls iter(thing) and pulls items until StopIteration. That's the same protocol generators use, which is why §3's generator material slots straight in on top of this.

Writing for i in range(len(xs)) is almost always a mistake. If you want items, iterate items. If you want both, use enumerate. Index arithmetic is where off-by-one bugs live:

for i in range(len(xs)): print(xs[i]) # C, transliterated for x in xs: print(x) # Python for i, x in enumerate(xs): print(i, x) # when you need both

Truthiness is a protocol, not a coincidence. if xs: calls __bool__, falling back to __len__. So empty containers are falsy without any special-casing in the language:

The trap in that table

if not count: fires for both “count is zero” and “count was never set.” When the difference matters — and with counts, prices and flags it always does — write if count is None: and say what you mean.

for … else is Python's most misread syntax. The else runs when the loop finished without hitting break — read it as “no break”, never as “otherwise”. It exists to kill the found = False flag variable:

for row in rows: if row.id == target: handle(row) break else: # no break — nothing matched raise KeyError(target)
05

Functions, arguments and return values

The single highest-value fact in this section: default arguments are evaluated once, when def runs — not on each call.

Everyone learns this by losing an hour to it. The def statement is executed like any other statement; it builds a function object and stores the defaults on that object. Every call thereafter reuses those same default objects. With an immutable default that's invisible. With a mutable one it's a shared, accumulating bucket.

Argument passing is neither “by value” nor “by reference.” Both terms come from languages with a different memory model and neither fits. Python passes the binding: the parameter becomes a new name for the caller's object. So a function can mutate what you passed, but cannot rebind your name — exactly the two cases in the §2 diagram.

Every function returns something. A function with no return returns None. So does a bare return. This is why xs = xs.sort() silently destroys your list: sort() mutates in place and returns None. You wanted sorted(xs).

06

Lambda functions

A lambda is an expression that evaluates to a function. def is a statement. That grammatical difference is the entire reason lambda exists — and the entire limit on what it can do.

Because it must be an expression, its body is a single expression whose value is returned implicitly. No statements: no if/else blocks (the ternary is an expression, so that's fine), no loops, no assignment, no try. It's not a lesser def; it's a function literal for places where a statement isn't allowed.

sorted(rows, key=lambda r: r.score) # idiomatic sorted(rows, key=lambda r: (-r.score, r.name)) # multi-key, note the tuple f = lambda x: x * 2 # don't — just use def def f(x): return x * 2 # same thing, and it has a name

PEP 8 says not to bind a lambda to a name, and the reason is practical rather than stylistic: a def carries its name into tracebacks and repr. A named lambda shows up as <lambda> in the stack trace, so you lose the one piece of information you wanted when something broke.

The late-binding trap

[lambda: i for i in range(3)] gives three functions that all return 2. A closure captures the variable, not its value at creation time, and by the time you call them the loop has finished. Bind it as a default — lambda i=i: i — which, per §5, is evaluated at definition time and freezes the value. The two traps in this note are the same mechanism read from opposite ends.

07

List, dict and set comprehensions

A comprehension isn't shorthand for a loop. It compiles to its own scope with a specialised opcode — which is why it's faster and why the loop variable doesn't leak.

Read the order once and it stops looking backwards: output expression, then the loops in the order you'd write them, then the filter.

All four forms use the same grammar, and the brackets pick the result type:

[x * 2 for x in xs] # list {x: x * 2 for x in xs} # dict — note the colon {x * 2 for x in xs} # set — dedupes for free (x * 2 for x in xs) # GENERATOR — lazy, not a tuple

That last one is the one that surprises people: parentheses don't give you a tuple comprehension, they give you a generator expression. There is no tuple comprehension; use tuple(...) around a genexp. The distinction is real work — sum(x*x for x in big) never materialises a list, so it costs constant memory.

Nested comprehensions read outer-to-inner, same order as the equivalent nested loops:

[c for row in grid for c in row] # flatten — for row, then for c [[c for c in row] for row in grid] # nested lists — inner is its own comprehension
Know when to stop

A comprehension is the right tool when it fits on one line and states a transformation. When it grows a second filter, a ternary and a nested loop, it has stopped being clearer than the loop it replaces. Comprehensions are for expressing what the collection is; the moment you need to explain how it's built, write the loop.

Retrieval bank

Cover the notes and answer from memory before opening anything. Retrieval you don't check can reinforce errors — and retrieval that feels easy isn't doing any work.

Why is b = a not a copy, and what is it instead?
Python names are labels bound to objects, not boxes holding values. b = a attaches a second label to the same object. Nothing is copied unless you explicitly ask for a copy.
Predict both: b.append(3) versus b = b + [3], where a and b name the same list.
append mutates the shared object, so a sees the change. b = b + [3] builds a new list and rebinds only b, leaving a on the original. Mutation reaches through every label; rebinding moves one.
Dynamically typed and strongly typed — what's the difference?
Dynamic: names have no declared type and can be rebound to anything. Strong: the object's type is enforced, so "3" + 4 raises TypeError rather than silently coercing. Python is both; JavaScript is dynamic but weak.
When is is the right operator, and why does testing it on integers mislead you?
Only for the singletons None, True, False. It appears to work on small ints because CPython caches −5 to 256 and interns short strings — an implementation detail, not a guarantee. == compares value; is compares identity.
What survives into the running program — a # comment or a docstring?
The docstring. It's bound to __doc__ and readable at runtime by help(), your IDE, pydoc and doctest. A # comment is discarded before bytecode exists.
if not count: — what two different situations does this conflate?
“count is zero” and “count is None” — both falsy. When a legitimate zero must be distinguishable from a missing value, write if count is None:. Also worth remembering: "0" and " " are truthy strings.
When does the else on a for loop run?
When the loop finished without hitting break. Read it as “no break”, never as “otherwise”. It exists to eliminate the found = False flag variable.
Explain the mutable default argument bug, and give the fix.
Defaults are evaluated once, when def executes, and stored on the function object — so a mutable default is one object shared by every call, accumulating state. Fix: default to None and build the real value inside the body (if bucket is None: bucket = []), because None is immutable and can't accumulate.
Why does xs = xs.sort() destroy your list?
list.sort() sorts in place and returns None, so you rebind xs to None. Use sorted(xs) for a new list, or call xs.sort() as a bare statement. General rule: Python's in-place methods return None precisely so this mistake is loud rather than silent.
What does LEGB stand for, and what causes UnboundLocalError?
Local, Enclosing, Global, Built-in — the order a name lookup walks outward, stopping at the first match. Reads walk outward; writes always target Local. Assigning to a name anywhere in a function makes it local for the whole function, so a read before that assignment finds an unfilled local instead of the global. Fix with global or nonlocal — or better, don't.
Why does [lambda: i for i in range(3)] produce three functions that all return 2?
A closure captures the variable, not its value at creation time; by the time you call them the loop has ended with i == 2. Fix by binding it as a default: lambda i=i: i — which works precisely because defaults are evaluated at definition time. Same mechanism as the mutable-default bug, read from the other end.
What does (x * 2 for x in xs) produce, and why does it matter?
A generator expression, not a tuple — there is no tuple comprehension. It's lazy, so sum(x*x for x in big) never materialises a list and costs constant memory. Wrap in tuple(...) if you actually want a tuple.
