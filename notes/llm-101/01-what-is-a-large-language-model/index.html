01

What “language modeling” means

What "language modeling" actually means
See it

Give a model the text "The capital of France is" and ask what comes next. What comes back is not a sentence. It is a table:

  " Paris"       0.87
  " located"     0.04
  " a"           0.02
  " home"        0.01
  " known"       0.01
  … 100,272 more rows, each a tiny number
                 ─────
  every row adds to  1.00

Probabilities are illustrative — they differ per model. The shape is always exactly this.

That table is the model's entire output for one step. Nothing else comes out.

Words
token
A word-piece. Not the same as a word. " Paris" is one token; "thermodynamics" is three (ther + m + odynamics). A model has a fixed list of them — 100,277 in the case above.
probability
A number between 0 and 1 saying how likely something is.
distribution
The whole table. Just a name for “every token, each with its probability.” They always add up to exactly 1.
Walk it

A sentence gets built by doing that once per token. Each step, one row is picked and glued onto the end, then the whole thing goes back in:

StepText going inTop of the tablePicked
1The capital of France is" Paris" 0.87" Paris"
2…France is Paris"." 0.61"."
3…France is Paris." It" 0.22" It"

Three steps, three tables. The model never wrote a sentence — it produced one table at a time, and something picked a row from each.

The rule

A language model is a thing that takes some text and gives you the probability of every possible next token.

That's the whole definition. Transformers, training, GPUs — all of it is machinery for making that one table more accurate.

A model is asked to write a 50-word answer. How many tables does it produce?

Show answer
Roughly 60 — one per token, and 50 words of ordinary English is about 60 tokens. Not one table for the answer: one table per token, each built from everything written so far.
02

How it learns to fill in that table

Next-token prediction intuition
See it

Take one real sentence from the internet. Cover the last token. Ask the model to guess it, then compare against what the sentence actually says:

sentence:  "The cat sat on the mat"
shown:     "The cat sat on the ___"

model says          truth is " mat"        score
─────────────────────────────────────────────────
" mat"   0.60   →   right, fairly sure  →  0.51
" floor" 0.30
" roof"  0.05

              a better model
" mat"   0.95   →   right, very sure    →  0.05

              a worse model
" mat"   0.01   →   right answer buried →  4.61

Score is -log(probability it gave the true token). Lower is better. These are real values: -log(0.60)=0.51, -log(0.95)=0.05, -log(0.01)=4.61.

Words
loss
That score. One number saying how wrong the model was on one guess. Zero means it was certain and correct.
training
Doing this billions of times and, after each one, nudging the model's internal numbers so the true token would have scored a bit higher next time.
self-supervised
Nobody had to label anything. The right answer was already sitting in the sentence — you just covered it up. That's why this could be done on the whole internet.
Walk it

Look at what the score does across those three cases. Going from 0.95 to 0.60 costs you 0.46. Going from 0.60 down to 0.01 costs 4.10. The penalty doesn't rise steadily — it explodes as the true answer's probability approaches zero.

So the thing training punishes hardest isn't being wrong. It's being confident and wrong. A model that says “probably A, but maybe B” is treated far more kindly than one that says “definitely A” and misses.

Where hallucination comes from

The table always adds to 1. Always. Even when the model has no idea, something has to receive that probability — there is no row for “I don't know.”

So a made-up answer isn't a malfunction. It's the same machinery working normally on a question it has nothing solid for.

The rule

Training is: cover up a token, let the model guess, score how much probability it put on the true one, nudge it to do better. Repeat about ten trillion times.

Nothing was labelled by hand. The text labelled itself.

Two models both get the answer right. One said 0.55, the other 0.99. Which is punished more, and is that fair?

Show answer
The 0.55 one (loss 0.60 vs 0.01). It's fair because the score rewards justified confidence, not just correctness. That's also why a model's own probabilities are a real signal about how sure it is — that behaviour was trained in from the first step.
03

Why guessing tokens produces reasoning

Why predicting the next token leads to reasoning-like behavior
See it

Same question, asked two ways. The only difference is whether the model is allowed to write anything before the answer:

A.  "17 × 24 = "
    → model emits one token.  It had one pass to
      get there.  Often wrong.

B.  "17 × 24 = ? Work step by step."
    → "17 × 20 = 340"        ← a pass
      "17 × 4  = 68"         ← a pass
      "340 + 68 = 408"       ← a pass
      "The answer is 408"    ← a pass

    Same model.  Roughly 20× more computation spent.
Words
a pass
One trip round the loop from §1. Producing one token takes exactly one pass, and one pass does a fixed amount of computation — it cannot try harder.
Walk it

In A, the model has one pass to go from "17 × 24 = " straight to a number. That's all the computation it will ever get for the problem.

In B, each written token goes back in as input (the loop in §1). So "17 × 20 = 340" is now text the model can read when computing the next token. It has offloaded a partial result onto the page and can build on it.

This is why the reasoning has to be visible. There's no hidden place to put it — writing it down is the only way the model can carry something from one pass to the next.

The rule

One pass buys a fixed amount of computation. Writing intermediate steps is how a model buys more, because its own output is the only thing it can add to its own input.

Squeezing a hard question into a one-line answer isn't efficiency — it caps how much thinking is possible.

Why can't the model just think harder in one pass instead of writing steps?

Show answer
Because a pass does a fixed amount of computation — it has no throttle. The only variable the model controls is how many passes it takes, and it gets one more pass per token it writes. More written tokens is literally more thinking.
04

What gets better when models get bigger

Emergence & scale laws (intuition, not research-heavy)
See it

Train the same design at four sizes and measure two things — the average loss from §2, and whether it can do 5-digit addition:

size        average loss      5-digit addition
──────────────────────────────────────────────
1 billion       3.2                  0%
7 billion       2.9                  0%
30 billion      2.6                  0%
150 billion     2.3                 61%

            smooth              a cliff
         and predictable       and a surprise

Illustrative numbers with the real shape: loss falls in a straight predictable line, task scores jump.

Words
parameters
The internal numbers that get nudged during training. “7 billion” means seven billion of them. Bigger usually means better, at a cost.
emergence
The name for what the right-hand column does — an ability that is absent at small scale and present at large scale, appearing in a jump rather than creeping up. This is the word people use for it; whether it is real or an artifact of the ruler is the point of this section.
scaling law
The observed fact that loss falls in a predictable line as size and data go up. Predictable enough to forecast a model you haven't built.
Walk it

Look at why the right column jumps while the left column doesn't. 5-digit addition is scored right-or-wrong. Get four digits correct out of five and you score zero.

So the model was steadily improving the whole time — that's the left column — but the measurement couldn't see any of it until the improvement crossed the line where every digit lands. The cliff is in the ruler, not in the model.

What this costs you in practice

Loss you can forecast. What the model can actually do you cannot.

So “the next model will be like this one but 10% better” is the wrong expectation. Abilities show up in jumps, and so do things that stop working. Test each new model on your own task rather than assuming.

The rule

Loss improves smoothly and predictably with scale. Task performance jumps — often because the test is pass-or-fail and hides the smooth progress underneath.

A benchmark reads 0% today. Should you assume it'll still be near 0% for a model twice the size?

Show answer
No. 0% may mean “improving steadily but not yet over the line.” A pass-or-fail score reads zero right up until it doesn't, so it can go 0% → 60% with nothing dramatic happening inside the model.
05

One general model, or one model per job

Foundation models vs task-specific models
See it

The job: decide whether a review is positive or negative. Two ways to get it done:

THE OLD WAY — build a model for this one job
  collect 20,000 reviews, label each by hand
  train a model that does only this
  → works well, ~3 milliseconds, very cheap
  → useless for anything else
  → new product category? start over

THE NEW WAY — ask a general model
  "Is this review positive or negative? {review}"
  → works well, no training, no labels, ~800 ms
  → same model also summarises, translates, writes code
  → hundreds of times the cost per call
Words
foundation model
A model trained on a huge amount of general text, not for any particular job, that can then be pointed at many jobs. “Foundation” describes the breadth it was trained on — not its size.
task-specific model
A model trained for exactly one job, and useless outside it.
Walk it

Neither column wins outright — read the trade rather than picking a side.

The old way is 250× faster and far cheaper per call, but you paid for 20,000 hand-labelled reviews before it did anything, and it's stuck at that one job.

The new way works this afternoon with no data at all, and the same model handles jobs you haven't thought of yet — but every call is slow and comparatively expensive.

Which is why the usual sequence is: use the general model to find out whether the thing is worth building, and only build a small specialised model once you know it is and the volume hurts.

The rule

A foundation model trades cost and speed for flexibility and a standing start. A task-specific model trades flexibility for being cheap and fast at the one thing.

“Foundation” means broadly trained and adaptable — not big.

You need to flag spam at 50,000 messages a second, and you have millions of labelled examples. Which do you reach for?

Show answer
Task-specific. All three conditions favour it: one narrow job, labels already in hand, and a volume where per-call cost and milliseconds dominate everything else.
06

Two kinds of model, two kinds of output

Generative vs representation models
See it

Give the same sentence to two different kinds of model. Look at what each hands back:

input:  "How do I reset my password?"

A generative model          a representation model
returns text                 returns numbers

"Go to Settings, then      [0.04, -0.21, 0.88,
 click Reset Password…"      0.13, -0.55, … ]

                             1,536 numbers. Always
                             1,536, for any input.
Words
generative model
Produces text, one token at a time — the loop from §1. This is what people mean by “an LLM.”
embedding
That fixed-length list of numbers. A position in space that stands for the meaning of the input.
representation model
Produces embeddings rather than text. Much smaller and much cheaper than a generative model.
Walk it

The numbers look meaningless on their own, and alone they are. They become useful the moment you have two of them, because similar meanings get similar numbers:

"How do I reset my password?"
"I forgot my login"          →  very close together
"What time do you close?"     →  far away

…even though the first two share almost no words.

That's the whole trick behind search that works on meaning rather than keywords. Turn 2 million documents into 2 million embeddings once. Turn the incoming question into one embedding. Find the closest few. It's a distance comparison, not a text search.

And it's why a real question-answering system runs both: the small cheap model finds the relevant documents, then the big expensive one reads them and writes the answer.

The rule

Generative models return text. Representation models return numbers that encode meaning, so that similar things end up near each other.

Most real systems use both, and they cost wildly different amounts.

Why not skip the small model and let the big one search the documents itself?

Show answer
Because it would have to read all two million for every question. Far too slow, far too expensive, and more text than it can hold at once. The cheap model's job is to cut two million down to five.
