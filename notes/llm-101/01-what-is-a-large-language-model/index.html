01

What “language modeling” means

What "language modeling" actually means
See it

Give a model the text "The capital of France is" and ask what comes next. What comes back is not a sentence. It is a table:

  " Paris"       0.87
  " located"     0.04
  " a"           0.02
  " home"        0.01
  " known"       0.01
  … 100,272 more rows, each a tiny number
                 ─────
  every row adds to  1.00

Probabilities are illustrative — they differ per model. The shape is always exactly this.

That table is the model's entire output for one step. Nothing else comes out.

Words
token
A word-piece. Not the same as a word. " Paris" is one token; "thermodynamics" is three (ther + m + odynamics). A model has a fixed list of them, its vocabulary: 100,277 for GPT-4's tokenizer (the one above, and the one Karpathy uses), 50,257 for GPT-2 in the exercise.
probability
A number between 0 and 1 saying how likely something is.
distribution
The whole table. Just a name for “every token, each with its probability.” They always add up to exactly 1.
logit
The raw score the network gives each token before it becomes a probability. Any number, even negative.
softmax
The step that turns logits into the table: raise e to each score, then divide each by the total.
Walk it

A sentence gets built by doing that once per token. Each step, one row is picked and glued onto the end, then the whole thing goes back in:

StepText going inTop of the tablePicked
1The capital of France is" Paris" 0.87" Paris"
2…France is Paris"." 0.61"."
3…France is Paris." It" 0.22" It"

Three steps, three tables. The model never wrote a sentence — it produced one table at a time, and a separate step, the sampler, picked a row from each.

The table itself comes out of the network in two moves. First every token gets a raw score, a logit. Then softmax turns the scores into probabilities. Pretend the vocabulary had three tokens:

                 " Paris"   " located"   " a"
logits              5.0        2.0        1.2
softmax           0.933      0.046      0.021   ← adds to 1
The top row isn't always the one picked

The walk-through above always took the top row. That's greedy picking. Chat models usually sample instead: roll a die weighted by the table, so " Paris" at 0.933 wins about 93 times in 100 and loses the rest.

Temperature divides the logits before softmax. At 0.5 the same scores give 0.9970 / 0.0025 / 0.0005, almost always the top row. At 2 they give 0.728 / 0.163 / 0.109, more variety. That's why the same prompt can come back different. Inference settings get their own note (§5).

The rule

A language model is a thing that takes some text and gives you the probability of every possible next token.

That's the whole definition. Transformers, training, GPUs — all of it is machinery for making that one table more accurate. A sampler then picks from it.

A model is asked to write a 50-word answer. How many tables does it produce?

Show answer
Roughly 60 — one per token, and 50 words of ordinary English is about 60 tokens. Not one table for the answer: one table per token, each built from everything written so far.

Predict first: what will the top next token be after "The capital of France is", and roughly how sure will the model be?

Show the script
# Section 01: see the table a language model actually outputs.
# Predict first: what will the top next token be after "The capital of France is"?
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("gpt2", clean_up_tokenization_spaces=True)
model = AutoModelForCausalLM.from_pretrained("gpt2")

text = "The capital of France is"
ids = tok(text, return_tensors="pt").input_ids
with torch.no_grad():
    scores = model(ids).logits[0, -1]      # one score for every possible next token
table = torch.softmax(scores, dim=-1)      # scores -> probabilities that add to 1

print(f"The table has {len(table):,} rows and they add up to {table.sum():.4f}\n")
top = torch.topk(table, 8)
for p, i in zip(top.values, top.indices):
    print(f"  {tok.decode(i)!r:14} {p:.3f}")

# Then try: change `text` to "The capital of Japan is", then to "I love eating".
Check your output

  ' the'         0.085
  ' now'         0.048
  ' a'           0.046
  ' France'      0.032
  ' Paris'       0.032
  ' in'          0.027
  ' also'        0.026

A real table: 50,257 rows adding to exactly 1. The top guess is ' the' at 0.085, with ' Paris' only fifth at 0.032.

What happens

Japan: ' the' 0.094, then ' Tokyo' 0.067. “I love eating”: ',' 0.064, ' and' 0.060, '.' 0.049 — when many continuations are reasonable, the table spreads thin and no row is large.

Worth knowing. GPT-2 is small and from 2019. The 0.87 for Paris earlier in the note was labelled illustrative; a modern large model does put most of its probability there. The shape of the output is the same either way — only how confident it is changes.

02

How it learns to fill in that table

Next-token prediction intuition
See it

Take one real sentence from the internet. Cover the last token. Ask the model to guess it, then compare against what the sentence actually says:

sentence:  "The cat sat on the mat"
shown:     "The cat sat on the ___"

model says          truth is " mat"        score
─────────────────────────────────────────────────
" mat"   0.60   →   right, fairly sure  →  0.51
" floor" 0.30
" roof"  0.05

              a better model
" mat"   0.95   →   right, very sure    →  0.05

              a worse model
" mat"   0.01   →   right answer buried →  4.61

Score is -log(probability it gave the true token). Lower is better. These are real values: -log(0.60)=0.51, -log(0.95)=0.05, -log(0.01)=4.61.

Words
loss
That score. One number saying how wrong the model was on one guess. Zero means it was certain and correct. Its full name is cross-entropy loss (categorical_crossentropy in the CampusX code).
training
Doing this over and over, nudging the model's internal numbers so the true tokens score a bit higher next time. Real runs nudge once per batch — about a million guesses in Karpathy's run — and the loss they print is the average over that batch.
self-supervised
Supervised learning where the text supplies its own labels. CampusX calls it “turning it into a supervised problem”: same thing. The right answer was already sitting in the sentence, so nobody labelled anything by hand, and it could run on the whole internet.
Walk it

Look at what the score does across those three cases. Going from 0.95 to 0.60 costs you 0.46. Going from 0.60 down to 0.01 costs 4.10. The penalty doesn't rise steadily — it explodes as the true answer's probability approaches zero.

So the thing training punishes hardest isn't being wrong. It's being confident and wrong. A model that says “probably A, but maybe B” is treated far more kindly than one that says “definitely A” and misses.

And one sentence isn't one example. Every position gets covered in turn, so a sentence of n tokens gives n − 1 guesses. This is CampusX's own example, split by word to keep it readable:

"Hi my name is Nitish"  →  4 training examples

Hi               →  my
Hi my            →  name
Hi my name       →  is
Hi my name is    →  Nitish

Why is the answer a table and not a single number? Token IDs are labels, not quantities. Token 4 isn't “bigger” than token 2, and a prediction of 2.7 would mean nothing. So this is classification over the whole vocabulary: one probability per token.

Where hallucination comes from

The table always adds to 1. Always. Even when the model has no idea, something has to receive that probability — there is no row for “I don't know.”

So a made-up answer isn't a malfunction. It's the same machinery working normally on a question it has nothing solid for.

The rule

Training is: cover up a token, let the model guess, score how much probability it put on the true one, nudge it to do better. Do it at every position of every sentence, across trillions of tokens (the FineWeb dataset Karpathy uses is 15 trillion).

Nothing was labelled by hand. The text labelled itself.

Two models both get the answer right. One said 0.55, the other 0.99. Which is punished more, and is that fair?

Show answer
The 0.55 one (loss 0.60 vs 0.01). It's fair because the score rewards justified confidence, not just correctness. That's also why a model's own probabilities are a real signal about how sure it is — that behaviour was trained in from the first step.

# Section 02: score how surprised a model is by each real next token.
# Predict first: which sentence gets the higher total loss, and at which word?
import math
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("gpt2", clean_up_tokenization_spaces=True)
model = AutoModelForCausalLM.from_pretrained("gpt2")

for text in ["The cat sat on the mat.", "The cat sat on the thermodynamics."]:
    ids = tok(text, return_tensors="pt").input_ids[0]
    with torch.no_grad():
        tables = torch.softmax(model(ids[None]).logits[0], dim=-1)
    print(text)
    total = 0.0
    for pos in range(1, len(ids)):
        p = tables[pos - 1, ids[pos]].item()   # probability given to the real next token
        loss = -math.log(p)
        total += loss
        print(f"   {tok.decode(ids[pos])!r:18} p = {p:.4f}   loss = {loss:.2f}")
    print(f"   total loss {total:.2f}\n")

03

Why guessing tokens produces reasoning

Why predicting the next token leads to reasoning-like behavior
See it

Same question, asked two ways. The only difference is whether the model is allowed to write anything before the answer:

A.  "17 × 24 = "
    → model emits one token.  It had one pass to
      get there.  Often wrong.

B.  "17 × 24 = ? Work step by step."
    → "17 × 20 = 340"        ← a pass
      "17 × 4  = 68"         ← a pass
      "340 + 68 = 408"       ← a pass
      "The answer is 408"    ← a pass

    Same model.  Roughly 20× more computation spent.
Words
a pass
One trip round the loop from §1. Producing one token takes exactly one pass, and one pass does a fixed amount of computation — it cannot try harder. It's fixed because the network has a fixed number of layers, about a hundred in a modern model (a longer context costs a little more, not much).
Walk it

In A, the model has one pass to go from "17 × 24 = " straight to a number. That's all the computation it will ever get for the problem.

In B, each written token goes back in as input (the loop in §1). So "17 × 20 = 340" is now text the model can read when computing the next token. It has offloaded a partial result onto the page and can build on it.

This is why the reasoning has to be visible. There's no hidden place to put it — writing it down is the only way the model can carry something from one pass to the next.

And the order matters. Suppose it writes "The answer is 408, because 17 × 20 = 340…". The 408 was still produced in one pass, before any working existed, so the working after it can't have helped. Karpathy calls that post-hoc justification. Working first, answer last.

The rule

One pass buys a fixed amount of computation. Writing intermediate steps is how a model buys more, because its own output is the only thing it can add to its own input.

Squeezing a hard question into a one-line answer isn't efficiency — it caps how much thinking is possible.

More passes isn't the same as right answers

Every written step is itself one pass, and any of them can slip. So when a step must be exact, Karpathy has the model write code and run it instead. Asked to count a row of dots, the model guessed 161; Python's .count() got the true 177. Written steps buy computation. Tools buy exactness.

Why can't the model just think harder in one pass instead of writing steps?

Show answer
Because a pass does a fixed amount of computation — it has no throttle. The only variable the model controls is how many passes it takes, and it gets one more pass per token it writes. More written tokens is literally more thinking.

04

What gets better when models get bigger

Emergence & scale laws (intuition, not research-heavy)
See it

Train the same design at four sizes and measure two things — the average loss from §2, and whether it can do 5-digit addition:

size        average loss      5-digit addition
──────────────────────────────────────────────
1 billion       3.2                  0%
7 billion       2.9                  0%
30 billion      2.6                  0%
150 billion     2.3                 61%

            smooth              a cliff
         and predictable       and a surprise

Illustrative numbers with the real shape: loss falls in a straight predictable line, task scores jump.

Words
parameters
The internal numbers that get nudged during training. “7 billion” means seven billion of them. Bigger usually means better, at a cost.
emergence
The name for what the right-hand column does — an ability that is absent at small scale and present at large scale, appearing in a jump rather than creeping up. This is the word people use for it; whether it is real or an artifact of the ruler is the point of this section.
scaling law
The observed fact that loss falls in a predictable line as two numbers go up: the parameters (N) and the amount of training text (D). Predictable enough to forecast a model you haven't built.
Walk it

Look at why the right column jumps while the left column doesn't. 5-digit addition is scored right-or-wrong. Get four digits correct out of five and you score zero.

So the model was steadily improving the whole time — that's the left column — but the measurement couldn't see any of it until the improvement crossed the line where every digit lands. Much of the cliff is in the ruler, not in the model.

That's the argument of Schaeffer and colleagues (2023): switch to a score that gives partial credit, or test on more questions, and many claimed emergent abilities turn into smooth curves. It's a strong case, not a closed one. The paper itself says emergence “may not be” a fundamental property of scale.

What this costs you in practice

Loss you can forecast. An average over many tests tends to rise with it too — Karpathy's example is every exam improving from GPT-3.5 to GPT-4. A single pass-or-fail task you can't forecast: it can sit at 0% and then jump.

So “the next model will be like this one but 10% better” is the wrong expectation for your task. Test each new model on it rather than assuming.

The rule

Loss improves smoothly and predictably with scale. Task performance jumps — often because the test is pass-or-fail and hides the smooth progress underneath.

A benchmark reads 0% today. Should you assume it'll still be near 0% for a model twice the size?

Show answer
No. 0% may mean “improving steadily but not yet over the line.” A pass-or-fail score reads zero right up until it doesn't, so it can go 0% → 60% with nothing dramatic happening inside the model.

05

One general model, or one model per job

Foundation models vs task-specific models
See it

The job: decide whether a review is positive or negative. Two ways to get it done:

THE OLD WAY — build a model for this one job
  collect 20,000 reviews, label each by hand
  train a model that does only this
  → works well, ~3 milliseconds, very cheap
  → useless for anything else
  → new product category? start over

THE NEW WAY — start from a general model
  prompt it:  "Is this review positive or negative? {review}"
  → works well, no training, no labels, ~800 ms
  → or fine-tune it on a few hundred labelled reviews
  → same model also summarises, translates, writes code
  → hundreds of times the cost per call
Words
foundation model
A big model pre-trained on huge, varied data with a general task — for text, next-token prediction from §2 — whose learning transfers to many other jobs. “Foundation” is the base you build on. In practice they're all big (billions of parameters, in CampusX's definition), but size isn't what makes one: a huge model trained for one narrow job is still task-specific.
task-specific model
A model trained for exactly one job, and useless outside it.
fine-tuning
Extra training of a pre-trained model on a small labelled set for your job. CampusX's analogy: engineering college is pre-training, the company's induction programme is fine-tuning.
Walk it

Neither column wins outright — read the trade rather than picking a side.

The old way is 250× faster and far cheaper per call, but you paid for 20,000 hand-labelled reviews before it did anything, and it's stuck at that one job.

The new way works this afternoon with no data at all if you prompt it, or with a few hundred examples if you fine-tune it. The same model handles jobs you haven't thought of yet — but every call is slow and comparatively expensive.

There's a second cost the old way hides: data, money and a team able to train a model from scratch. CampusX's point is that most companies had none of these, so their one-job models came out mediocre. A foundation model arrives already strong, because someone else paid for its three stages: pre-training on huge data (the expensive part), alignment (people rank its answers and it's rewarded for the best), then fine-tuning or prompting for your job.

Task-specific still wins when no general model covers the job — CampusX's example is predicting a cricket innings' final score — or when volume makes per-call cost dominate. Hence the usual sequence: use the general model to find out whether the thing is worth building, and only build a small specialised one once you know it is and the volume hurts.

The rule

A foundation model trades cost and speed for flexibility and a standing start. A task-specific model trades flexibility for being cheap and fast at the one thing.

What makes a model a foundation is general pre-training that transfers, not size alone — though in practice they are all big.

You need to flag spam at 50,000 messages a second, and you have millions of labelled examples. Which do you reach for?

Show answer
Task-specific. All three conditions favour it: one narrow job, labels already in hand, and a volume where per-call cost and milliseconds dominate everything else.

# Section 05: build a task-specific model from labelled examples.
# Predict first: what will it say about "an absolute masterpiece"?
import time
from collections import Counter

train = [
    ("loved it, great acting", "pos"), ("wonderful and moving", "pos"),
    ("great fun, loved the ending", "pos"), ("brilliant, wonderful cast", "pos"),
    ("boring and far too long", "neg"), ("terrible plot, awful acting", "neg"),
    ("awful, boring, a waste", "neg"), ("terrible ending, hated it", "neg"),
]

weights = Counter()                       # training: count which words go with which label
for text, label in train:
    for word in text.replace(",", "").split():
        weights[word] += 1 if label == "pos" else -1

def classify(text):
    score = sum(weights[w] for w in text.lower().replace(",", "").split())
    return "pos" if score > 0 else "neg" if score < 0 else "no idea"

tests = ["great acting, wonderful", "boring and awful",
         "an absolute masterpiece", "summarise this review for me"]
start = time.perf_counter()
results = [classify(t) for t in tests]
took = time.perf_counter() - start
for t, r in zip(tests, results):
    print(f"  {t!r:32} -> {r}")
print(f"\n{len(tests)} predictions in {took * 1e6:.0f} microseconds")

Two kinds of model, two kinds of output

Generative vs representation models
See it

Give the same sentence to two different kinds of model. Look at what each hands back:

input:  "How do I reset my password?"

A generative model          a representation model
returns text                 returns numbers

"Go to Settings, then      [0.04, -0.21, 0.88,
 click Reset Password…"      0.13, -0.55, … ]

                             1,536 numbers. Always
                             1,536, for any input.
Words
generative model
Produces text, one token at a time — the loop from §1. LangChain, in the CampusX video, calls these language models. “LLM” usually means this kind, but the word stretches: CampusX's foundation-models video counts BERT, a representation model, as an LLM.
embedding
That fixed-length list of numbers. A position in space that stands for the meaning of the input.
representation model
Produces embeddings rather than text. LangChain calls it an embedding model. Much smaller: the one in the exercise has 22.7 million parameters, against 124 million for the smallest GPT-2 and billions for chat models.
cosine similarity
How close two embeddings are, measured by the angle between them: 1 means pointing the same way, 0 means unrelated.
Walk it

The numbers look meaningless on their own, and alone they are. They become useful the moment you have two of them, because similar meanings get similar numbers:

"How do I reset my password?"
"I forgot my login"          →  very close together
"What time do you close?"     →  far away

…even though the first two share almost no words.

That's the whole trick behind search that works on meaning rather than keywords. Turn 2 million documents into 2 million embeddings once. Turn the incoming question into one embedding. Find the closest few by cosine similarity. It's an angle comparison, not a text search. The document embeddings are stored once in a vector database, and each question embeds only itself; CampusX calls this step retrieve.

And it's why a real question-answering system runs both: the small cheap model finds the relevant documents, then the big expensive one reads them and writes the answer.

The rule

Generative models return text. Representation models return numbers that encode meaning, so that similar things end up near each other.

Most real systems use both, and they cost wildly different amounts.

Why not skip the small model and let the big one search the documents itself?

Show answer
Because it would have to read all two million for every question. Far too slow, far too expensive, and more text than it can hold at once. The cheap model's job is to cut two million down to five.

# Section 06: turn sentences into numbers and compare them by meaning.
# Predict first: which sentence is closest to "How do I reset my password?"
import numpy as np
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2", tokenizer_kwargs={"clean_up_tokenization_spaces": True})
sentences = ["How do I reset my password?", "I forgot my login", "What time do you close?"]
vectors = model.encode(sentences, normalize_embeddings=True)

print(f"Each sentence becomes {vectors.shape[1]} numbers.")
print("First five for sentence one:", np.round(vectors[0][:5], 3), "\n")
for sentence, v in zip(sentences, vectors):
    print(f"  {vectors[0] @ v:.3f}  {sentence}")    # 1.0 means identical meaning
