01

Why the old approach hit a wall

Why RNNs failed at scale
See it

Before transformers, models read text the way you do — one word at a time, carrying a memory forward. Count the steps for a 1,000-token document:

RNN — must go in order
  tok 1 → tok 2 → tok 3 → … → tok 1000
  1,000 steps, each waiting for the one before

Transformer — all positions at once
  tok 1  tok 2  tok 3  …  tok 1000
    ↓      ↓      ↓         ↓
  1 step. Every token processed simultaneously.
Words
RNN
Recurrent Neural Network. Reads one token, updates a memory, reads the next. The design that dominated before 2017.
hidden state
That carried-forward memory. One fixed-size bundle of numbers holding everything seen so far.
parallel
Work that can happen at the same time. GPUs are fast only at this; give one sequential work and it idles.
gradient
The signal training sends back through the network to say which numbers to nudge, and by how much.
Walk it

Two problems, and the second is the one that actually killed it.

Information decays. For a fact at token 1 to matter at token 1,000, it has to survive 999 rewrites of one fixed-size memory. It mostly doesn't. Training makes it worse: the gradient that should teach the model “token 1 mattered” gets multiplied by one factor per step on its way back. If each factor is a little below 1 it vanishes (0.9 multiplied 100 times is 0.00003); a little above 1 and it explodes (1.1 multiplied 100 times is about 13,781). LSTMs, a gated kind of RNN, patched much of this.

You can't use the hardware. Step 500 needs step 499's output, so no amount of GPU will run them together. Training on a large corpus would have taken years of wall-clock time — not because the maths was hard, but because it refused to go in parallel. LSTMs didn't fix this one: they still read one token at a time.

The thing that's easy to get backwards

Decay was real, but LSTMs patched most of it. What no recurrent design could patch was the one-token-at-a-time order, so RNNs couldn't be trained big enough to find out how good they might get.

The transformer's real contribution was removing the sequential dependency during training. Everything else follows from being able to spend a thousand GPUs on one model.

The rule

RNNs process in order, so training can't be parallelised and long-range information degrades. Transformers process every position at once — which is what made scale possible.

§1 said generation is one token at a time. Doesn't that make transformers sequential too?

Show answer
Yes — at generation time. The parallelism is in training, where the whole text is already known so every position can be scored at once. Generation is still one token per pass. Training parallel, generation serial: that split explains most of what follows.

exercises/llm-101/02/01_sequential_vs_parallel.py

Predict first: how much faster is doing all 1,000 rows at once than one after another?

Show the script
# Section 01: the same multiplications, done one after another or all at once.
# Predict first: how much faster is doing all 1,000 rows at once?
import time
import numpy as np

rng = np.random.default_rng(0)
n = 1000
x = rng.standard_normal((n, 256))          # n tokens, 256 numbers each
W = rng.standard_normal((256, 256)) / 16

def one_after_another():                    # RNN-style: step i needs step i-1 first
    h = np.zeros(256)
    for i in range(n):
        h = np.tanh(x[i] @ W + h)

def all_at_once():                          # transformer-style: no step waits on another
    np.tanh(x @ W)

def best_of_5(f):                           # timings on a laptop are noisy, so keep the best run
    runs = []
    for _ in range(5):
        start = time.perf_counter(); f(); runs.append(time.perf_counter() - start)
    return min(runs)

a, b = best_of_5(one_after_another), best_of_5(all_at_once)
print(f"one after another : {a * 1000:7.2f} ms")
print(f"all at once       : {b * 1000:7.2f} ms   ({a / b:.0f}x faster)")

# Then try: set n = 4000. Which time grows faster?
Check your output
one after another :   13.20 ms
all at once       :    3.33 ms   (4x faster)

About 4–5× on this 2016 MacBook (13.2 ms against 3.3 ms). Same multiplications; the only difference is whether each one waits for the last.

Then try: rewrite one_after_another so it doesn't need the loop.

What happens

You can't. Each h needs the previous h, so step 500 cannot start before step 499 finishes. That dependency, not the maths, is what stopped RNNs using a GPU.

Worth knowing. A laptop CPU shows only a modest, noisy gap — at 4,000 rows it nearly vanished here. The real difference shows up on a GPU, which runs thousands of independent multiplications at once but can't speed up a chain where each step waits.

02

The problem attention solves

Attention mechanism intuition
See it

Read this sentence and answer what it refers to:

"The animal didn't cross the street because it was too tired."
                                            ↑
"The animal didn't cross the street because it was too wide."
                                            ↑

First one: it is the animal. Second: it is the street. One word changed at the very end, eight tokens away, and the meaning of it flipped.

So whatever processes it must be able to reach back and pull in the right earlier word — and which word is right depends on a token that comes after it.

Words
attention
A step where every token looks at every other token, decides how relevant each one is, and mixes them into itself accordingly.
weights
The relevance numbers. One per pair of tokens, always adding to 1 for each looking token. Also called attention weights or alignment scores.
Walk it

The RNN answer was “carry a memory forward and hope the animal is still in it.” The attention answer is direct: let it look at every token in the sentence at once and take mostly the relevant one.

Distance stops mattering. Token 900 reaching token 3 is the same single operation as reaching token 899 — there are no hops to survive.

Attention wasn't invented for sentences like this one. It arrived in 2014 for translation, bolted onto RNNs. There the RNN squeezed the whole input sentence into one summary vector before writing the output, and beyond about 25–30 words that summary overflowed. The fix was to let each output word take a fresh weighted mix of all the input words: to write “लाइट” for “Turn off the lights,” look mostly at lights. Transformers kept the mixing and threw away the RNN.

The rule

Attention lets any token pull information directly from any other token in one step, with the mixture decided by content rather than by distance.

Why is “distance stops mattering” the important part?

Show answer
Because in an RNN, information from token 3 reaching token 900 had to survive 897 rewrites of a fixed-size memory. With attention it's one operation, identical in cost and fidelity to reaching a neighbour.

Predict first: will it attend differently in the two sentences? They differ only in the last word, “tired” versus “wide”.

Show the script
# Section 02: look inside a real model and see which words "it" pulls from.
# Predict first: will "it" attend differently in the two sentences?
# (They differ only in the last word: "tired" versus "wide".)
import torch
from transformers import AutoModel, AutoTokenizer

tok = AutoTokenizer.from_pretrained("gpt2", clean_up_tokenization_spaces=True)
model = AutoModel.from_pretrained("gpt2", output_attentions=True, attn_implementation="eager")

for text in ["The animal didn't cross the street because it was too tired",
             "The animal didn't cross the street because it was too wide"]:
    ids = tok(text, return_tensors="pt").input_ids
    words = [tok.decode(i).strip() for i in ids[0]]
    look_from = words.index("it")
    with torch.no_grad():
        attn = torch.stack(model(ids).attentions)    # [layer, batch, head, from, to]
    w = attn[:, 0, :, look_from, :].mean(dim=(0, 1))  # average over 12 layers x 12 heads
    w[0] = 0                                           # drop the first token (see the gotcha)
    w = w / w.sum()
    print(text)
    for i in torch.argsort(w, descending=True)[:4]:
        print(f"   {words[i]:<8} {w[i]:.2f}")
    print()

# Then try: set look_from = len(words) - 1, so you measure from the last word instead.

03

Self-attention, one step at a time

Self-attention explained visually
The setup
Where we areSection 02: a word's meaning depends on the words around it.
What we haveThe sentence the river bank, each word stored as a list of numbers (its embedding).
What we wantA version of bank whose numbers mean river bank.
How1 · Score→2 · Shares→3 · Mix

I've picked the numbers by hand so you can read them. A trained model learns its own, but the arithmetic is identical. Each word also has a fourth number, 0 for all three, so it's left out.

          water  money  generic
the     [  0.3    0.3     2.5  ]   filler word
river   [  2.6    0.0     0.5  ]   very water
bank    [  1.6    1.6     0.8  ]   equally both

bank is equally water and money. By the end it shouldn't be. In CampusX's terms, we're turning a static embedding (one vector per word, whatever the context) into a contextual one.

Step 1 · Score

A dot product multiplies two lists position by position and adds the results. Big numbers in the same places give a big score.

bank·the    =  1.6×0.3 + 1.6×0.3 + 0.8×2.5  =  2.96
bank·river  =  1.6×2.6 + 1.6×0.0 + 0.8×0.5  =  4.56   ← shared water
bank·bank   =  1.6×1.6 + 1.6×1.6 + 0.8×0.8  =  5.76

river outscores the because it shares bank's water number.

Step 2 · Shares

Divide each score by √4 = 2 (four numbers per word), then apply softmax: raise e to each, divide by the total. The shares always add to 1.

         score   ÷ 2     e^x     share
the       2.96   1.48    4.39    0.137
river     4.56   2.28    9.78    0.306
bank      5.76   2.88   17.81    0.557
                        ─────    ─────
                        31.98    1.000

So the new bank is 13.7% the, 30.6% river, 55.7% itself.

Step 3 · Mix

Take a weighted average of the three words, one number at a time:

water  =  0.137×0.3 + 0.306×2.6 + 0.557×1.6  =  1.73
money  =  0.137×0.3 + 0.306×0.0 + 0.557×1.6  =  0.93

river added 0.795 to water and nothing to money. That's what tips it.

Result
                      water   money
bank on its own        1.60    1.60   ambiguous
"the river bank"       1.73    0.93   leans water
"the savings bank"     0.93    1.73   leans money

Same bank, same three steps. Only the neighbour changed: savings is river with its water and money numbers swapped.

Why divide by √4

Softmax exaggerates gaps. Skip the divide and bank's shares become 0.045 / 0.221 / 0.734 — less blending, more copying itself.

The real reason is size. The dot product of two random lists of d numbers has a variance of about d (measured: 4.0 at d = 4, 64 at 64, 514 at 512). At 512 numbers a typical score sits about 23 from zero, softmax goes to nearly 1.0 and 0.0, and the small shares stop learning because their gradients vanish. Dividing by √d brings the variance back to 1 at any size. Strictly, d is the length of the key vector; here that's the embedding's four numbers.

Query, key, value

Here each word used its own numbers for everything. That version has nothing to learn — dot product, softmax, average — so it gives the same blend whatever the task. A real model multiplies each embedding by three learned matrices, WQ, WK and WV, shared by every word, to get a query (what this word is looking for), a key (what it offers to be matched on) and a value (what it hands over if chosen). The names come from a dictionary lookup: d[query] finds the matching key and returns its value. The three steps don't change.

The rule

Self-attention rebuilds each word from its neighbours: score them with dot products, turn the scores into shares with softmax, then mix their numbers by those shares.

Why did bank take 30.6% from river but only 13.7% from the?

Show answer
Because river scored higher in step 1 (4.56 against 2.96). It shares bank's large water number, while the's large number sits in the generic slot, where bank is small. Softmax then widens that gap.

              [2.6, 0.0, 0.5, 0.0],
              [1.6, 1.6, 0.8, 0.0]])

04

Why there are many attentions, not one

Multi-head attention purpose
See it

One set of weights produces one blend. But a token usually needs several unrelated things at once:

"The keys to the cabinet were on the table."

to get "were" right, you need:
  which noun is the subject  →  look at "keys"    (not "cabinet")
  what tense is this          →  look at the wider sentence
  what does it connect to     →  look at "on the table"

One row of weights cannot point three places at once.
Words
head
One complete attention calculation with its own WQ, WK, WV. A model runs many side by side.
multi-head attention
Running H heads in parallel over the same tokens, joining their outputs, and mixing them with one more learned matrix, WO.
Walk it

Take a model with 4,096 numbers per token and 32 heads. Each head multiplies the full vector by its own learned WQ, WK, WV, projecting it down to 128 numbers, and runs the whole score-soften-mix in that smaller space. The 32 outputs of 128 are joined back into 4,096, and WO mixes them into the final result. The original paper did the same with 512 numbers and 8 heads of 64; GPT-3 uses 96 heads of 128.

The exercise below fakes the projection by handing each head a fixed slice of the numbers, so you can see the effect. Real heads each see the whole vector, through weights they learn.

Because each head has its own weights, each is free to learn a different notion of “relevant.” When people inspect trained models they find heads that track grammatical subjects, heads that match quotes to speakers, heads that mostly look at the previous token.

Note what this doesn't cost: 32 heads of 128 dims is the same total width as 1 head of 4,096. You get several relationships for roughly the price of one.

Don't over-read the specialisation

“This head does grammar” is a useful story, not a guarantee. Heads are found by gradient descent, not assigned. Many do something no one can name, and pruning a supposedly-critical head often changes little.

The rule

One head produces one blend, so it can capture one kind of relationship. Multi-head attention runs many in parallel, each through its own learned projection of the same vector, letting a token gather several different things at once.

Why split into 32 heads of 128 rather than run 32 full-width ones?

Show answer
Cost. 32 heads × 128 dims is the same total work as one head at 4,096. Thirty-two full-width heads would be 32× the compute for a benefit nobody has shown you need. The split buys variety for free.

05

Three ways to wire it up

Encoder-only vs Decoder-only vs Encoder-Decoder
See it

The only structural difference between the three families is which tokens each token is allowed to look at. Real shares for the same three words as section 03 — this time with every word's row, not just bank's:

EVERYONE SEES EVERYONE      ONLY LOOK LEFT
         the river  bank             the river  bank
the     0.78  0.09  0.14    the     1.00     —     —
river   0.06  0.73  0.21    river   0.08  0.92     —
bank    0.14  0.31  0.56    bank    0.14  0.31  0.56

an encoder                  a decoder

Real softmax output. The dashes are positions blocked before the softmax, so the remaining weights in each row still add to 1.

Words
encoder
Every token sees the whole sequence, both directions. Good for understanding text you already have.
decoder
Each token sees only itself and what came before. Necessary for generating, where the future doesn't exist yet.
causal mask
The block that enforces “left only”: a matrix of 0s and minus infinity, added to the scores after the √d divide and before the softmax, which turns minus infinity into exactly 0. Zeroing shares after the softmax would break the add-to-1 rule.
Walk it

Look at the first row of each. In the encoder, the takes 14% of bank — it can already see a word that comes after it. In the decoder its row is 1.00, then nothing: it can only see itself, because when the model was learning to produce the first token, nothing after it had been written.

Now look at the last row. bank's row is identical in both — 0.14, 0.31, 0.56 — because bank is the last word, so “look left” already means “look at everything.” The mask only ever takes something away from the earlier words.

That gives three families:

FamilySeesTrained toGood atExamples
Encoder-onlyeverythingfill in hidden wordsclassifying, embeddingBERT, e5
Decoder-onlyleft onlypredict the next tokengenerating textGPT, Claude, Llama
Encoder-decoderboth, in two stacksrebuild hidden spansfixed input → outputT5, BART

This is the §1 split again, seen from underneath. Representation models are encoders; generative models are decoders. The mask is the mechanism.

The encoder-decoder's decoder has one extra attention step, cross-attention: its queries come from the output being written, its keys and values from the encoder's reading of the input. That's the translation setup from section 02.

The rule

Encoder, decoder and encoder-decoder differ by which positions attention is allowed to reach. Everything else — the layers, the maths — is the same.

Why can't a generative model just use an encoder and see everything?

Show answer
Because during training it would see the answer. Predicting token 5 while able to look at token 5 is not a task — it's copying, and it teaches nothing usable at generation time, when nothing to the right exists. CampusX calls this data leakage.

# Section 05: the only difference between an encoder and a decoder.
# Predict first: what will the first row look like in the decoder?
import numpy as np

words = ["the", "river", "bank"]
E = np.array([[0.3, 0.3, 2.5, 0.0], [2.6, 0.0, 0.5, 0.0], [1.6, 1.6, 0.8, 0.0]])
scores = E @ E.T / np.sqrt(4)

def softmax_rows(m):
    e = np.exp(m - m.max(axis=1, keepdims=True))
    return e / e.sum(axis=1, keepdims=True)

encoder = softmax_rows(scores)
masked = scores.copy()
masked[np.triu_indices(3, k=1)] = -np.inf   # block every word from seeing later words
decoder = softmax_rows(masked)

for name, m in [("encoder: sees everything", encoder), ("decoder: looks left only", decoder)]:
    print(name)
    for w, row in zip(words, m):
        print(f"   {w:<6}" + "".join(f"{v:7.2f}" for v in row))

06

Why almost every LLM is decoder-only

Why decoder-only models dominate LLMs
See it

Take one 512-token passage and count how many training signals each design squeezes out of it:

decoder-only — every position predicts the next
  511 predictions from one passage

encoder-style — hide about 15% and predict those
  ~76 predictions from the same passage

  6.7× more learning per token of text you own

Computed: 511 vs 512 × 0.15. The 15% figure is BERT's masking rate.

Walk it

Three reasons, in the order they matter.

More signal per token. The numbers above. When text is the scarce resource, 6.7× is decisive. What makes all 511 happen in one pass is the mask from section 05 plus teacher forcing: during training, each position's input is the true previous token from the data, not the model's own guess, so every input is known up front and all positions run at once. Without that, a 300-token target would need 301 passes one after another (CampusX's count).

One design does every job. Any task can be phrased as text completion — classify, translate, summarise. An encoder needs a task-specific head bolted on; a decoder just needs a different prompt.

Simplicity scales. One stack, one objective, one mask. Fewer moving parts to tune when a training run costs eight figures.

Not “better,” just better-suited

Encoders still win where they fit. For search and classification, a small encoder beats a large decoder at a fraction of the cost — which is exactly the two-model split from §1.

Decoder-only dominates general-purpose models. It didn't win everywhere.

The rule

Decoder-only won because it extracts far more training signal per token, handles every task through one interface, and stays simple enough to scale.

Why does “more signal per token” matter so much?

Show answer
Because high-quality text is finite. Compute you can buy; a bigger internet you cannot. Getting 6.7× the learning from the same corpus is worth more than any architectural elegance.

07

Order, position, and how much fits

Context window & positional encoding
See it

Run attention on two sentences that mean opposite things, and look at the vector it produces for dog:

"dog bites man"  → "dog" comes out as  [1.74, 0.55, 1.16, 0.00]
"man bites dog"  → "dog" comes out as  [1.74, 0.55, 1.16, 0.00]

                                        byte-for-byte identical

Real output. Attention is a weighted sum, and addition doesn't care about order.

Attention on its own is completely blind to word order. Position has to be added separately, or the model can't tell who bit whom.

Words
positional encoding
Extra numbers added to each token that encode where it is. Position 1 gets a different pattern from position 2.
context window
The most tokens a model can attend over at once. Everything outside it does not exist to the model.
Walk it

Why not just number the tokens 1, 2, 3? CampusX walks through why each simple idea fails. Raw counts grow without limit (a book reaches 100,000), and training hates huge numbers. Dividing by the length fixes the size but makes position 2 worth 1.0 in a two-word sentence and 0.5 in a four-word one. A single sine wave stays between −1 and 1 but repeats, so two positions can collide.

The original paper's answer: pairs of sine and cosine waves, each pair slower than the last, added to the embedding rather than glued on (gluing would double its size):

PE(pos, 2i)   = sin(pos / 100002i/d)
PE(pos, 2i+1) = cos(pos / 100002i/d)      pos starts at 0
position   0:  +0.000 +1.000 +0.000 +1.000
position   1:  +0.841 +0.540 +0.100 +0.995
position   2:  +0.909 -0.416 +0.199 +0.980
position  50:  -0.262 +0.965 -0.959 +0.284

Real values for d = 8, first four numbers shown.

The pairs have a useful property. Moving from any position to the one k steps later is the same fixed rotation of each sine–cosine pair, wherever you start, so “k tokens apart” looks the same everywhere. Modern models build directly on that: RoPE rotates the query and key vectors by position instead of adding numbers to the embedding.

Why context windows cost so much

Every token attends to every token, so the attention pattern has length2 entries and the work grows with the square of the length. Double the context and attention gets four times more expensive; ten times the context is a hundred times the attention cost.

That quadratic is why long context was hard for years, and why a million-token window is an engineering achievement rather than a bigger number in a config file.

The rule

Attention ignores order, so position is added to each token explicitly. The context window is how far attention can reach — and its cost grows quadratically, not linearly.

Going from 8k to 128k context is 16× the tokens. Roughly what happens to attention cost?

Show answer
About 256× — 16 squared. That gap between 16× the text and 256× the work is why long-context models are priced the way they are, and why cutting what you send matters more than it looks.

Show the script
# Section 07: attention on its own cannot tell word order.
# Predict first: will "dog" come out the same in both sentences?
import numpy as np

V = {"dog": [2.0, 0.3, 0.5, 0.0], "bites": [0.4, 2.2, 0.3, 0.0], "man": [1.8, 0.4, 1.9, 0.0]}

def attend(words, add_position=False):
    E = np.array([V[w] for w in words], dtype=float)
    if add_position:                               # the sine/cosine pattern from the note
        pos = np.arange(len(words))[:, None]
        E = E + np.hstack([np.sin(pos), np.cos(pos), np.sin(pos / 10), np.cos(pos / 10)])
    s = E @ E.T / 2
    w = np.exp(s - s.max(axis=1, keepdims=True))
    return (w / w.sum(axis=1, keepdims=True)) @ E

for add in (False, True):
    a = attend(["dog", "bites", "man"], add)[0]    # "dog" is word 0 here...
    b = attend(["man", "bites", "dog"], add)[2]    # ...and word 2 here
    label = "with position " if add else "without position"
    print(f"{label}  dog/bites/man {np.round(a, 2)}   man/bites/dog {np.round(b, 2)}")

# Then try: make the position signal tiny by writing E = E + 0.01 * np.hstack(...).
# Can you still tell the two sentences apart?

08

The KV cache

KV cache intuition (important for engineering)
See it

From §1: generating runs the model once per token, on everything written so far. Count the work for a 1,000-token answer:

without caching — redo the whole thing each step
  step 1: 1 token   step 2: 2 tokens   …   step 1000: 1000
  total = 500,500 token-steps

with caching — keep what you already computed
  total = 1,000 token-steps

  500× less work, for exactly the same output

Computed: 1000×1001/2 versus 1000.

Words
KV cache
Stored intermediate values for tokens already processed, so each one is computed once instead of once per subsequent step.
prefill
Processing your prompt. Parallel, so fast — this is time-to-first-token.
decode
Generating each new token. Serial, one pass each — this is the rest of the wait.
Walk it

When token 900 attends to token 3, the values it needs from token 3 are the same ones token 899 needed. Nothing about token 3 changed. So keep them.

Which converts a quadratic amount of work into a linear one — and buys it with memory:

per token:      2 (keys and values) × 32 layers × 1024 × 2 bytes
              = 128 KiB per token

  1,000 tokens  →   0.12 GiB
  8,192 tokens  →   1.00 GiB
128,000 tokens  →  15.62 GiB   ← for ONE conversation

Computed for an 8B-class model. Sizes vary, the shape doesn't.

That number explains a lot of things you'll otherwise find mysterious. Why long conversations get expensive rather than just slow. Why a server handles far fewer concurrent long chats than short ones. Why providers charge separately for input and output tokens — prefill and decode are genuinely different operations on the hardware.

The cache is per conversation, and it is not free

Every simultaneous conversation needs its own. Serving 100 users at 8k context is 100 GiB of cache before the model weights. This, not the weights, is usually what limits how many users a GPU can serve.

The same trick across requests: prompt caching

Providers also keep the cache for a prompt prefix that many requests share, such as a long system prompt, and bill later hits cheaply. CampusX's example is a text-to-SQL feature: 400 tokens in, 100 out, 50,000 times a day, at the video's prices of $10 per million input tokens and $50 per million output. That's $0.009 a query. If 350 of the 400 input tokens are a cached prefix billed at $1 per million, it drops to $0.00585, 35% less.

The first write costs extra ($12.50 per million), and the cache expires after 5 minutes unless it's hit again. It barely helps RAG, where most of the prompt changes on every request.

The rule

The KV cache stores each token's attention values once instead of recomputing them every step — trading memory for a roughly 500× reduction in work on a long answer.

It's why generation is memory-bound rather than compute-bound, and why context length shows up on your bill twice. Kept across requests for a shared prefix, the same cache is what prompt caching sells.

Your chat app slows down as a conversation goes on, even though replies stay short. Why?

Show answer
Every new token attends over the whole history, which keeps growing, and the cache grows with it — 128 KiB per token. The replies aren't longer; each token is doing more work and touching more memory. Trimming or summarising history is the fix.

Predict first: roughly how much faster is the cached version at 400 tokens?

Show the script
# Section 08: generate tokens with and without a KV cache, and time both.
# Predict first: roughly how much faster is the cached version at 400 tokens?
import time
import numpy as np

rng = np.random.default_rng(0)
d, n = 64, 400
W = rng.standard_normal((d, d)) / 8
tokens = rng.standard_normal((n, d))

start = time.perf_counter()                        # no cache: redo every token each step
for t in range(1, n + 1):
    keys = tokens[:t] @ W
    _ = keys @ tokens[t - 1]
no_cache = time.perf_counter() - start

start = time.perf_counter()                        # cache: compute each token's key once
cache = np.empty((n, d))
for t in range(1, n + 1):
    cache[t - 1] = tokens[t - 1] @ W
    _ = cache[:t] @ tokens[t - 1]
with_cache = time.perf_counter() - start

print(f"key rows computed, no cache : {n * (n + 1) // 2:,}")
print(f"key rows computed, cache    : {n:,}")
print(f"time, no cache : {no_cache * 1000:6.1f} ms")
print(f"time, cache    : {with_cache * 1000:6.1f} ms   ({no_cache / with_cache:.0f}x faster)")
per_token = 2 * 32 * 1024 * 2                      # keys and values, 32 layers, 1024 wide, 2 bytes
print(f"\ncache memory for an 8B-class model: {per_token // 1024} KiB per token, "
      f"{per_token * 8192 / 1024**3:.2f} GiB at 8,192 tokens")

# Then try: set n = 800. Does the gap double, or more?
Check your output

key rows computed, cache    : 400
time, no cache :   15.6 ms
time, cache    :    3.4 ms   (5x faster)
